# v0.3.61-r2 Ship Pilot Context Windows Gate

Runtime target: Starfield 1.16.244.0  
DLL ProductVersion/FileVersion expected: **0.3.61.0 / 0.3.61.0**

## Gate A — normal on-foot baseline

1. Start on foot with a known firearm equipped.
2. Confirm its existing adaptive-trigger profile is present.
3. Confirm current health lightbar behavior is normal.
4. Fire once and confirm existing weapon haptics/controller-speaker behavior is unchanged.

## Gate B — enter pilot context

1. Board the ship and enter/take control of the pilot seat.
2. Confirm the log contains exactly one:
   `Ship pilot context: ENTER source=SpaceshipHudMenu authority=menu`
3. Confirm handheld adaptive-trigger resistance is gone/neutral.
4. Confirm the on-foot health lightbar is no longer lingering; v0.3.61 owns no ship lightbar presentation yet, so neutral/off is expected.
5. Confirm no handheld sustained weapon haptic or controller-speaker loop lingers.
6. Confirm v0.3.61 does **not** add a ship rumble, ship trigger profile, ship speaker cue, or other ship feel yet.

## Gate C — in-flight overlays

While still piloting:

1. Open/close Data Menu.
2. Open/close Pause Menu.
3. Exercise any normal short Fader/Cursor transition available.
4. Confirm no `EXIT` or `INVALIDATE` occurs solely from those overlays.
5. Confirm ship pilot ownership stays active.

## Gate D — clean pilot exit

1. Land/dock normally and leave the pilot seat.
2. Confirm exactly one:
   `Ship pilot context: EXIT source=SpaceshipHudMenu refresh=fresh-on-foot`
3. Confirm exactly one subsequent line beginning with:
   `Ship pilot context: ON-FOOT-REFRESH`
4. Ideally it reads:
   `Ship pilot context: ON-FOOT-REFRESH weapon=fresh health=fresh`
5. Confirm the currently equipped weapon's correct adaptive-trigger profile returns.
6. Confirm the health lightbar returns from a fresh health sample.
7. Confirm no neutral/stale ship-context state remains after the on-foot refresh.

## Gate E — loading/travel invalidation and resolution

Run both shapes if practical.

### E1 — load returns to the same cockpit HUD

1. Re-enter pilot context.
2. Trigger a travel/loading sequence while ship context is active.
3. Confirm `LoadingMenu` produces exactly one:
   `Ship pilot context: INVALIDATE source=LoadingMenu refresh=deferred-until-fresh-context`
4. If `SpaceshipHudMenu` remains open through the load, confirm `LoadingMenu` close produces exactly one:
   `Ship pilot context: RESUME source=LoadingMenu-close evidence=SpaceshipHudMenu-still-open`
5. Confirm no new `SpaceshipHudMenu` open is required to regain ship ownership.
6. Confirm handheld trigger/lightbar/haptics/weapon-speaker state remains neutral/suppressed after `RESUME`.
7. When `SpaceshipHudMenu` later closes normally, confirm exactly one:
   `Ship pilot context: EXIT source=SpaceshipHudMenu refresh=fresh-on-foot`
8. Confirm one subsequent `Ship pilot context: ON-FOOT-REFRESH ...` line.

### E2 — cockpit HUD closes during the load

1. From pilot context, trigger a load where `SpaceshipHudMenu` closes before `LoadingMenu` closes.
2. Confirm exactly one `INVALIDATE` when loading begins.
3. Confirm the HUD close itself does not create a duplicate exit while loading is still active.
4. When `LoadingMenu` closes, confirm exactly one:
   `Ship pilot context: EXIT source=LoadingMenu-close reason=SpaceshipHudMenu-closed-during-load refresh=fresh-on-foot`
5. Confirm one subsequent `Ship pilot context: ON-FOOT-REFRESH ...` line.
6. Confirm the correct on-foot adaptive trigger and health lightbar return from fresh observations.

In both shapes, there must be no stale duplicate `EXIT`, no cached controller-state restoration, and no handheld effect restart while ship ownership is active.

## Gate F — frozen regression spot checks

1. Test Va'ruun Starstorm sustained body feel; it must retain the accepted **1.60 sustained-body tuning**.
2. Test Arc Welder sustained haptics on foot.
3. Test Cutter sustained haptics on foot.
4. Test one ballistic weapon.
5. Test one finite weapon controller-speaker cue.
6. Open the main menu and confirm the v0.3.60 controller-speaker startup/prewarm behavior still works.

## Pass criteria

Approve v0.3.61 only if all are true:

- pilot entry is detected exactly once;
- clean pilot exit is detected exactly once;
- loading invalidation happens immediately and resolves as either `RESUME` or a deferred on-foot `EXIT`;
- Data/Pause/Fader/Cursor overlays do not falsely end pilot context;
- handheld adaptive-trigger/lightbar ownership is neutralized during ship context;
- handheld sustained haptics and weapon-speaker playback cannot linger or restart while piloting;
- clean exit rebuilds on-foot trigger/lightbar state from fresh observations;
- no stale ship/on-foot state survives loading, exit, disconnect, or shutdown;
- frozen weapon/haptics/speaker behavior remains correct;
- Starstorm accepted sustained-body feel remains unchanged;
- v0.3.60 main-menu controller-speaker startup behavior remains unchanged.

If `SpaceshipHudMenu` appears while the player is demonstrably **not** piloting, do not tune around it. Preserve the log and stop promotion; that means pilot authority needs a separate reconnaissance pass.
