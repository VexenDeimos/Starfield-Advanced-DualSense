# v0.3.64 Ship Laser Reconnaissance — Windows + Hardware Gate

Runtime marker: `0.3.64-ship-laser-recon`

Expected DLL versions:

- ProductVersion: `0.3.64.0`
- FileVersion: `0.3.64.0`

## Scope

This build is diagnostic-only for the laser ship-weapon family. It keeps the hardware-accepted v0.3.63-r6 ballistic ship-gun behavior unchanged and adds no laser vibration, laser adaptive-trigger firing effect, synthetic cadence, or normalized laser-fire semantic.

The recon path observes zero-external Starfield Wwise traffic only while pilot authority is active. For the focused test, isolate a laser weapon on the **R2-controlled ship weapon group** and do not fire the other groups. The probe records exact event ID, Wwise game object, Starfield callsite, returned playing ID, R2 value, and trigger-relative phase.

A 180 ms pre-press window can recover Wwise posts that precede the first qualifying controller sample. A 250 ms post-release window captures possible stop/power-down traffic. Neither window authorizes haptics. DataMenu/PauseMenu, loading invalidation, pilot exit, and shutdown clear the probe.

## Startup log gate

Confirm:

```text
StarfieldDualSense 0.3.64-ship-laser-recon runtime start
Ship ballistic haptics: ACTIVE ... forwardFirstShot=hardware-alias+180ms-real-R2 automaticHeartbeat=same-event+same-gameObject+held-R2 ...
Ship laser recon: ACTIVE target=laser diagnosticOnly=yes control=R2 ... prePressWindowMs=180 postReleaseWindowMs=250 ... hapticOutput=none triggerOutput=unchanged ballisticBaseline=r6-frozen
```

The ballistic activation line must still describe the accepted r6/r5 behavior. The laser line must explicitly say `diagnosticOnly=yes` and `hapticOutput=none`.

## Focused hardware run

Use a ship with a **laser weapon assigned to R2**. If the current ship has multiple weapon types on R2, temporarily rearrange the ship weapon groups so R2 fires only the laser under test.

1. Enter the pilot seat and verify the accepted propulsion texture and baseline R2 resistance still feel normal.
2. With the ship stationary or in a quiet open area, tap R2 once. Note whether you hear/see one laser shot, a short burst, or another behavior. No new laser-specific vibration should occur in this diagnostic build.
3. Wait about two seconds.
4. Hold R2 for 2–3 seconds, then release cleanly.
5. Wait about one second so the post-release tail and burst summary can flush.
6. Repeat one 2–3 second hold and release.
7. Open DataMenu once while still in the pilot seat, close it, then perform one final short laser burst.
8. Quit normally and send the fresh log plus a short description of the laser's audible/visual firing behavior.

## Expected recon evidence

A trigger pull should produce one press line:

```text
Ship laser recon: trigger burst=<n> action=press r2=<value> recoveredPrePress=<n> diagnosticOnly=yes
```

Wwise candidates inside the burst window appear as:

```text
Ship laser recon: Wwise burst=<n> phase=pre-press|held|post-release seq=<n> event=0x........ gameObject=0x... callsite=Starfield+0x... r2=<value> deltaUs=<signed> knownBallistic=yes|no returnedPlayingId=<n>
```

Release produces:

```text
Ship laser recon: trigger burst=<n> action=release r2=0 ... diagnosticOnly=yes
```

After the 250 ms tail, each distinct event/object pair gets a summary:

```text
Ship laser recon summary: burst=<n> heldUs=<n> event=0x........ gameObject=0x... posts=<n> firstDeltaUs=<n> lastDeltaUs=<n> minIntervalUs=<n> maxIntervalUs=<n> phases=pre|held|post|... knownBallistic=yes|no interpretation=diagnostic-only
```

### What we are looking for

- **Repeated-fire model:** the same non-ballistic event/object repeats through `phase=held` at a stable native interval.
- **Start/stop sustained model:** one event/object appears around press/start and a different event appears in `phase=post-release`, with little or no repeated held traffic.
- **Layered model:** one start event plus one or more repeatedly posted/long-lived events during the hold, possibly followed by a distinct release/stop event.

Do not infer laser authority from a single noisy event. The useful candidate should repeat across the isolated hardware bursts with the same event/object/lifecycle pattern.

## Acceptance for the recon build

- v0.3.63-r6 ballistic tap/hold behavior remains unchanged.
- Propulsion and Data/Pause menu suppression remain unchanged.
- No new laser-specific haptic or adaptive-trigger firing effect is felt.
- Laser recon lines appear only while pilot/R2 burst authority is relevant and stop after release/menu/lifecycle invalidation.
- The final log provides a repeatable candidate lifecycle that can drive the next laser implementation build.
