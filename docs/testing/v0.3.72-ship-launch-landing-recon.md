# v0.3.72 Ship Launch/Landing Reconnaissance

## Scope

This build is diagnostic-only. It observes physical ship launch and landing boundaries plus nearby native Wwise traffic so a later haptics build can be based on repeatable engine evidence rather than guessed timing.

Runtime marker: `0.3.72-ship-launch-landing-recon`  
ProductVersion/FileVersion: `0.3.72.0`

## Exact reconnaissance behavior

- The existing `ShipPropulsionState` is the state authority; no new memory writer or synthetic timer is introduced.
- The first fresh ship-state observation after pilot acquisition is an anchor only.
- `landed=true -> false` with neither side docked creates a **takeoff** boundary.
- `landed=false -> true` with neither side docked creates a **touchdown** boundary.
- Any transition where the previous or current state has `docked=yes` is suppressed.
- Wwise observations are buffered for 2000 ms before the boundary and collected for 2000 ms after it.
- At most 256 Wwise samples are retained per report.
- Each sample keeps exact sequence, event ID, game object, callsite RVA, returned playing ID, pre/post phase, and signed `deltaUs` from the boundary.
- Report lines tag already-accepted ballistic, laser, Proton Beam, missile, and EM weapon events so they can be excluded from launch/landing candidate analysis.
- DataMenu/PauseMenu, loading invalidation, pilot exit, pilot resume/re-entry, and shutdown clear recon state. A fresh ship state must anchor again afterward.
- There is no new launch/landing `GameEventType`, `HapticEffectKind`, adaptive-trigger presentation, controller-speaker cue, lightbar effect, or vibration output.

## Hardware capture

Use a ship that begins **landed on a planetary surface and not docked**.

1. Enter the pilot seat and wait at least two seconds without firing ship weapons or opening DataMenu/PauseMenu.
2. Launch normally. After the ship becomes airborne, remain in normal flight for at least three seconds.
3. Land normally. After touchdown, remain landed for at least three seconds.
4. If convenient, repeat one more launch/landing cycle to distinguish repeatable events from one-offs.
5. Exit cleanly and send the fresh `StarfieldDualSense(...).log`.

This build should add **no new controller feel** during launch or landing. The useful output is the diagnostic log.

Expected takeoff boundary shape:

```text
Ship launch/landing recon: boundary=takeoff transition=... beforeLanded=yes afterLanded=no ... diagnostic-only
Ship launch/landing recon report: transition=... boundary=takeoff samples=... preMs=2000 postMs=2000 ...
Ship launch/landing recon report: transition=... boundary=takeoff phase=pre|post deltaUs=... event=0x... gameObject=0x... callsite=Starfield+0x... returnedPlayingId=... diagnosticOnly=yes
```

Expected touchdown boundary shape:

```text
Ship launch/landing recon: boundary=touchdown transition=... beforeLanded=no afterLanded=yes ... diagnostic-only
Ship launch/landing recon report: transition=... boundary=touchdown samples=... preMs=2000 postMs=2000 ...
```

The goal of the capture is to identify repeatable candidates for takeoff initiation/spool, liftoff, touchdown impact, and landing-completion/settling. No candidate is promoted from a single run.
