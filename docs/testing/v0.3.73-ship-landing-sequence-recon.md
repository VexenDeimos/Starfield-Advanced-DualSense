# v0.3.73 Ship Landing-Sequence Reconnaissance

## Scope

This build remains **diagnostic-only**. v0.3.72 proved that the authoritative `landed=true -> false` takeoff boundary is repeatable and gives a stable native Wwise sequence. v0.3.73 leaves that takeoff path unchanged and adds a second reconnaissance path for landings that cross Starfield's travel/loading transition, where a live `landed=false -> true` sample is usually unavailable.

Runtime marker: `0.3.73-ship-landing-sequence-recon`  
ProductVersion/FileVersion: `0.3.73.0`

## Exact reconnaissance behavior

### Frozen state-boundary path

- The first fresh ship-state observation after pilot acquisition is still an anchor only.
- `landed=true -> false` with neither side docked still creates a **takeoff** boundary.
- `landed=false -> true` with neither side docked still creates a **touchdown** boundary when Starfield actually exposes one.
- Any state transition involving `docked=yes` is still suppressed.
- State-boundary reports retain the same 2000 ms pre-window, 2000 ms post-window, and 256-sample cap used by v0.3.72.

### New landing-sequence path

- The probe remembers the most recent authoritative airborne, non-docked ship state while the player is piloting.
- Opening DataMenu/PauseMenu still clears buffered Wwise evidence and active state-boundary reports. The last authoritative ship state is retained only so a landing load can be identified after the starmap/menu closes.
- An airborne `FaderMenu` transition starts a **landing-sequence candidate**. `LoadingMenu` can serve as a fallback start if the fader event was missed.
- The candidate is bounded to 30 seconds and still retains at most 256 Wwise samples.
- Diagnostic Wwise capture is allowed to remain armed across this candidate's `LoadingMenu` transition even after normal pilot authority is invalidated.
- Production ship weapon gates, propulsion haptics, triggers, lightbar behavior, speaker behavior, and other gameplay effects remain governed by their existing pilot/menu authority and are not granted landing-load authority.
- If `SpaceshipHudMenu` stays open and pilot authority resumes after loading, the candidate is canceled as ordinary in-ship travel.
- If `SpaceshipHudMenu` closes during loading, `LoadingMenu` closes, and then `FaderMenu` closes, the probe emits a **landing-sequence** report.
- A landing-sequence report is explicitly `stateBoundaryObserved=no`; it is a lifecycle correlation report, not a claim that a specific Wwise event is the physical touchdown instant.
- Each Wwise sample records its exact sequence, event ID, game object, callsite RVA, returned playing ID, signed `deltaUs`, and the contemporaneous open/closed state of `GalaxyStarMapMenu`, `FaderMenu`, `LoadingMenu`, and `SpaceshipHudMenu`.
- The report also records menu-timing deltas for the starmap close, fader open, loading open, ship-HUD close, loading close, and fader close when observed.
- Pilot lifecycle changes outside an active landing candidate and shutdown still discard stale reconnaissance evidence.
- There is still no launch/landing `GameEventType`, `HapticEffectKind`, trigger effect, speaker cue, lightbar effect, or new vibration output.

## Hardware capture

Use a destination that actually plays a visible ship landing sequence. Some fixed locations can skip the landing cinematic, so a normal planetary/moon landing site is preferable.

1. Start landed and enter the pilot seat.
2. Launch normally. No special takeoff action is required; this also gives us another v0.3.72-style takeoff sample for comparison.
3. Fly to another planet or moon if necessary.
4. From the starmap, choose a surface destination that produces the normal landing sequence.
5. Once the landing/travel sequence begins, do not open PauseMenu or make unrelated menu changes. Let the loading/cinematic/fader sequence finish naturally.
6. After arrival, remain on the surface for at least five seconds, then quit cleanly.
7. Send the fresh `StarfieldDualSense(...).log`.

This build should add **no new launch or landing controller feel**. The useful output is the diagnostic log.

Expected landing-sequence summary shape:

```text
Ship launch/landing recon report: transition=... boundary=landing-sequence samples=... anchor=FaderMenu-open-or-LoadingMenu-open beforeLanded=no stateBoundaryObserved=no galaxyStarMapClosedDeltaUs=... faderOpenedDeltaUs=... loadingOpenedDeltaUs=... spaceshipHudClosedDeltaUs=... loadingClosedDeltaUs=... faderClosedDeltaUs=... diagnosticOnly=yes
```

Expected per-Wwise sample shape:

```text
Ship launch/landing recon report: transition=... boundary=landing-sequence phase=pre|post deltaUs=... seq=... event=0x... gameObject=0x... callsite=Starfield+0x... returnedPlayingId=... menus=map:open|closed,fader:open|closed,loading:open|closed,hud:open|closed ... diagnosticOnly=yes
```

The goal is to identify which native Wwise events repeat at landing-sequence initiation, descent/engine transition, touchdown/gear impact, and settling. No event should be promoted to production haptics from a single capture.
