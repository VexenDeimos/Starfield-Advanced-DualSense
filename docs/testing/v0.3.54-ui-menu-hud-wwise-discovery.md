# v0.3.54 UI/Menu + HUD Wwise Discovery

v0.3.54 is a diagnostic-only hardware evidence build. It reuses the existing Wwise `PostEvent` interception and adds one bounded 120-second UI/menu + HUD observation session. It does not play UI/HUD sounds through the DualSense and does not change existing weapon audio, VO, haptics, adaptive triggers, lightbar, touchpad, HID arbitration, USB routing, or normal Starfield audio.

The probe is enabled only when `DebugLogging = true`. The first qualifying target-menu open starts the one-shot session. `HUDMenu`, `HUDMessagesMenu`, loading/fader menus, and dialogue-only menus do not start it by themselves.

## Exact hardware discovery run

1. Start Starfield and load a save.
2. Open Inventory and move selection several times.
3. Open/close item-detail or nested inventory views when available.
4. Back out.
5. Open Map / Star Map and perform several navigation and confirm/back actions.
6. Open Skills and perform several navigation actions.
7. Open Missions and perform several navigation actions.
8. Open Data Menu and Pause Menu and perform several navigation/confirm/back actions.
9. Return to normal gameplay.
10. Trigger one or more easy HUD notifications/popups during the remaining capture time if practical.
11. Let the 120-second window expire, or quit normally after sufficient evidence is captured.
12. Send the resulting `StarfieldDualSense(...).log` for candidate analysis.

Expected health markers include:

```text
UI audio discovery: START ... durationMs=120000
UI audio discovery: COMPLETE ... dropped=0
```

The final summary also reports candidate count, transition-correlation count, HUD-period candidate count, and transition-ring drops. `dropped>0` does **not** mean Starfield's game audio failed; the original Wwise call remains authoritative. It means the diagnostic evidence is incomplete, so rerun the discovery pass before promoting UI/HUD candidates.

## Player-facing UI/HUD sound control

v0.3.54 does not add UI/HUD playback, so `SpeakerScannerUI` does not disable the diagnostic observation session. When hardware evidence is later promoted into actual controller-speaker behavior, those UI/HUD sounds must use the existing `SpeakerCategory::ScannerUI` category and honor `SpeakerScannerUI = false`. `ControllerSpeaker = false` remains the master switch for all controller-speaker output.
