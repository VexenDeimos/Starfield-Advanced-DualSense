# v0.3.62 Propulsion Haptics Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add the first real ship propulsion haptics using the hardware-proven native throttle/effective-throttle/velocity signals without changing ship weapons, ship triggers, ship lightbar, ship speaker, damage, or frozen on-foot behavior.

**Architecture:** Keep native Starfield signal acquisition in `GameStateAdapter`, normalize it into a small transport-independent `ShipPropulsionState`, map that state to a `HapticContinuousState` in a pure core helper, and let `HapticsManager` own the ship continuous channel only while pilot authority is active. Extend `HapticMixer` with two authored continuous kinds: normal propulsion and boost. Lifecycle events remain the hard ownership boundary and clear ship haptics immediately.

**Tech Stack:** C++23, CommonLibSF/SFSE, existing WASAPI DualSense haptics backend, xmake, portable GCC/Clang tests, Python source regressions.

**Spec:** `docs/superpowers/specs/2026-09-07-ship-effects-design.md`

## Global Constraints

- ProductVersion/FileVersion remain `0.3.62.0`.
- Runtime marker becomes `0.3.62-propulsion-haptics`.
- Native flight-control observation stays passive/read-only.
- `+0x68` is throttle target, `+0x6C` effective throttle, `+0x70` velocity.
- Boost requires the native >1 throttle state and corroborating non-full boost fuel; recharge alone is not boost.
- Ship entry/resume owns the haptic context; loading/invalidation/exit hard-clear it.
- No ship weapon, speaker, adaptive-trigger, lightbar, damage, targeting, docking, or grav effects in this slice.
- Preserve Starstorm 1.60 sustained body, Arc Welder/Cutter lifecycles, Auto-Rivet, melee, Magsniper, recoil, and all prior on-foot behavior.
- No Git metadata is present in the working snapshot; use file-level SHA checkpoints instead of commits.
