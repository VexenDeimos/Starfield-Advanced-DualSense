# Starfield Advanced DualSense v0.2.47 — Cutter Continuous Haptics Design

Date: 2026-08-28
Status: Approved in-chat design, written-spec review pending
Base: v0.2.46 Ballistic Family Haptics (PASS / LOCKED)

## 1. Goal

Add authored controller-body haptics for the Cutter's continuous mining beam without weakening the project's confirmed-game-event authority model.

The Cutter must feel like a powered mining tool rather than a sequence of gunshots. A real Starfield `weaponFireStart` animation marker authorizes the continuous haptic effect. Live R2 travel then controls the effect's intensity and frequency. R2 input alone must never fabricate beam haptics.

This milestone is Cutter-only. Novablast charge behavior and all discrete weapon-family haptics remain unchanged.

## 2. Non-goals / frozen behavior

v0.2.47 must not retune or restructure any frozen behavior from earlier milestones:

- Cutter adaptive-trigger behavior remains unchanged, including its proven sustained 18 Hz construction-equipment trigger texture.
- Eon, Maelstrom, Microgun, Bridger, Negotiator, and all other locked adaptive-trigger profiles remain unchanged.
- v0.2.43 USB/WASAPI haptics transport remains unchanged except for recognizing one additional continuous effect kind.
- v0.2.44 Novablast continuous charge haptics remain unchanged.
- v0.2.45 discrete shotgun, laser, and particle haptics remain unchanged.
- v0.2.46 ballistic-family haptics remain unchanged.
- h4 HID arbitration remains byte-for-byte frozen.
- Fire-marker source identity and filtering remain unchanged.
- Touchpad, lightbar, semantic input, speaker behavior, and controller connection logic remain unchanged except for the narrowly required R2 observer notification described below.
- No Novablast discharge thump is added in this milestone.
- Hardware testing proved the confirmed-start + R2-stop model can become stale when Cutter energy depletes while R2 remains held, so the follow-up v0.2.47 build activates the previously deferred real-marker heartbeat/timeout refinement described below.

## 3. Existing authority that v0.2.47 reuses

The current FireMarkerBridge already distinguishes the Cutter's sustained start marker from ordinary repeated fire markers:

- `weaponFireStart` routes as `FireMarkerAction::SustainedStart` for sustained-energy weapons.
- The bridge normalizes accepted markers to the existing `GameEventType::WeaponFired` event while preserving the exact marker text in `GameEvent::text`.
- The existing adaptive-trigger engine already treats `weaponFireStart` as the Cutter's one authoritative sustained-fire start and ignores the repeated `WeaponFire` markers as individual kicks.

v0.2.47 reuses this same normalized event. No new FireMarkerBridge hook, source, relocation, or `GameEventType` is required.

## 4. Continuous haptic type

Extend `HapticContinuousKind` with:

```cpp
CutterBeam
```

The existing `HapticContinuousState` structure remains sufficient:

```cpp
struct HapticContinuousState
{
    HapticContinuousKind kind{ HapticContinuousKind::None };
    float gain{ 0.0F };
    float level{ 0.0F };
};
```

The existing packed latest-value backend state remains unchanged structurally; the new enum value is encoded through the existing kind byte.

## 5. Cutter authorization state

`HapticsEngine` gains one internal boolean state:

```cpp
bool _cutterBeamAuthorized{ false };
```

This state means only that Starfield has confirmed a Cutter beam start for the current trigger pull. It is not itself an assertion that R2 remains held.

### 5.1 Authorization start

While the equipped profile is exactly `Cutter`:

- A normalized `GameEventType::WeaponFired` whose marker text is exactly `weaponFireStart` sets `_cutterBeamAuthorized = true`.
- That event does not create a discrete `HapticCommand`.
- Repeated Cutter `WeaponFire` markers do not create discrete haptics and do not independently authorize a new beam.
- Empty marker text is not accepted as Cutter haptic authorization. The haptics path requires the real preserved marker text so tests or R2 activity cannot accidentally bypass the confirmed-start rule.

### 5.2 Authorization clear

Cutter authorization clears immediately when any of these occurs:

- live R2 reaches the existing release threshold: `r2 <= 12`;
- a weapon is equipped/swapped;
- the game enters a paused state;
- `Shutdown` is received;
- controller disconnect/worker shutdown sends the existing observer zero-clear.

After authorization is cleared, raising R2 again cannot resume Cutter haptics. A new exact `weaponFireStart` marker is required.

An arbitrary `MenuOpened` event is not a blanket clear because Starfield emits non-pausing HUD/menu events during normal gameplay. `GamePaused` is the semantic pause boundary.

### 5.3 Energy-depletion liveness refinement

Hardware acceptance exposed the deferred edge case: Starfield can stop the Cutter beam because its internal energy meter is empty while the player continues holding R2. The already-observed repeated real `WeaponFire` markers therefore become a liveness heartbeat only; they still do not create discrete recoil/haptic pulses and cannot authorize a beam by themselves. `weaponFireStart` arms a 300 ms liveness deadline, each real repeated `WeaponFire` refreshes it, and expiry clears both Cutter body haptics and the sustained adaptive-trigger texture. After expiry, a new exact `weaponFireStart` is required before held R2 can produce Cutter feedback again.

## 6. Live R2 behavior

The Cutter uses the existing live R2 observer path that was introduced for Novablast. No second input polling path is created.

While Cutter is equipped:

1. If `r2 <= 12`, clear `_cutterBeamAuthorized` and return `None`.
2. If `_cutterBeamAuthorized == false`, return `None` regardless of R2 travel.
3. If authorized and `r2 > 12`, return `CutterBeam`.

The normalized control level is:

```text
u = clamp((r2 - 24) / 231.0, 0, 1)
```

This intentionally uses the existing press threshold, 24, as the start of the variable-strength range. If an authorized pull falls between 13 and 23 during release travel, the Cutter remains active at `u = 0` until it reaches the true release threshold of 12, then becomes exact silence.

Overall gain continues to use the weapon profile's existing haptic rating and global strength:

```text
gain = clamp((Cutter.hapticRating / 10) * HapticStrength, 0, 1)
```

The current Cutter haptic rating is 4, so at `HapticStrength = 1.0`, nominal gain is `0.4`.

## 7. R2 observer threshold correction

The current read-only R2 observer notifies on:

- the first valid sample;
- 16-value bucket changes (`r2 >> 4`);
- crossing the Novablast/press threshold at 24.

That is insufficient for Cutter's approved immediate stop rule because values 0-15 share one bucket. A transition such as `15 -> 12` could otherwise be missed.

Therefore the observer must additionally notify when the existing release-threshold state changes across 12. Conceptually track:

```text
aboveReleaseThreshold = r2 > 12
```

and notify when that boolean changes, in addition to the existing first-sample, bucket-change, and `r2 >= 24` crossing rules.

This is still a read-only observer. It must not call `EffectsEngine`, synthesize `WeaponFired`, alter adaptive-trigger hysteresis, or change HID output ownership.

The controller's existing adaptive-trigger path remains behaviorally unchanged.

## 8. HapticsManager event/data flow

`HapticsManager` continues to serialize `HapticsEngine` access under `_engineMutex` and stores the latest observed R2 in `_lastR2`.

Events that can mutate continuous Cutter authorization must trigger an immediate continuous-state reevaluation using `_lastR2`, so the audio backend sees the state change without waiting for the next R2 bucket update.

At minimum, reevaluate after:

- `WeaponFired` — so exact `weaponFireStart` can immediately activate the beam using the already-known R2 position;
- `WeaponEquipped` — clears the previous authorization and continuous state;
- `GamePaused` — clears Cutter authorization and continuous state;
- `Shutdown` — clears all continuous state and saved R2.

The existing `handleRightTriggerInput()` path remains the live level/stop update path.

Backend submission failures remain haptics-only failures and cannot affect the controller/HID path.

## 9. Cutter waveform / continuous texture

The approved first-pass feel is a layered powered mining-tool vibration rather than gun recoil.

For normalized R2 level `u` and profile/global gain `g`:

```text
body frequency:  75 + 40u Hz
                    -> 75 Hz at low pull
                    -> 115 Hz at full pull

grit frequency: 190 + 70u Hz
                    -> 190 Hz at low pull
                    -> 260 Hz at full pull

amplitude:       g * (0.30 + 0.65u)

signal mix:      0.72 * body
               + 0.28 * grit
```

### 9.1 Attack and continuity

- New Cutter activation gets a 6 ms attack ramp.
- Updating `u` while Cutter remains active must not restart oscillator phase or the attack ramp.
- A continuous-kind change may restart the new kind's attack; ordinary level changes may not.
- The signal is symmetric on actuator channels 3 and 4.
- Channels 1 and 2 remain exact zero/reserved.
- Final mixed actuator values remain clamped to `[-1, 1]`.

### 9.2 Stop behavior

There is no release tail.

When Cutter state becomes `None`, the Cutter contribution is exact zero on the next rendered audio block. This is deliberate so releasing R2, swapping weapons, pausing, disconnecting, or shutting down cannot leave a stale mining buzz.

## 10. Mixer coexistence

`HapticMixer` continues to support finite discrete voices and one latest-value continuous layer.

The continuous branch supports both:

- `NovablastCharge` — existing waveform and behavior unchanged;
- `CutterBeam` — new waveform above.

Finite voices are mixed first, then the active continuous layer is added, then actuator channels are clamped. Reserved channels 1 and 2 remain zero.

`empty()` continues to report false whenever any continuous state other than `None` is active so WASAPI does not mark active Cutter blocks silent.

## 11. Failure and lifecycle behavior

The existing fail-soft model remains mandatory:

- If no compatible DualSense 4-channel/48 kHz endpoint exists, HID features continue normally.
- `setContinuous()` failure affects only haptics.
- Endpoint loss tears down/reconnects audio transport without disturbing adaptive triggers or other controller features.
- The latest continuous state remains the backend's source of truth across audio endpoint reconnects.
- Controller disconnect emits zero through the observer and clears Cutter authorization before a later reconnect can resume anything.
- Reconnecting while R2 is held cannot restart Cutter haptics without a new confirmed `weaponFireStart` after authorization was cleared.
- `AdvancedHaptics=false` installs no haptics R2 observer and starts no audio backend, as before.

## 12. Testing strategy

### 12.1 HapticsEngine semantic tests

Add focused tests proving:

1. Cutter equip alone emits no discrete or continuous haptic.
2. R2 travel alone cannot authorize Cutter haptics.
3. Cutter repeated `WeaponFire` without prior `weaponFireStart` cannot authorize haptics.
4. Exact `weaponFireStart` authorizes Cutter continuous haptics.
5. Cutter `weaponFireStart` creates no discrete `HapticCommand`.
6. At `HapticStrength = 1.0`, Cutter gain is 0.4 from its existing haptic rating.
7. Authorized Cutter with `r2 = 24` produces `CutterBeam`, gain 0.4, level 0.
8. Authorized Cutter with `r2 = 255` produces level 1.
9. Higher R2 produces a higher level than lower R2.
10. `r2 <= 12` clears authorization and returns `None`.
11. After release clear, later R2 travel cannot restart Cutter without a new `weaponFireStart`.
12. Weapon swap clears authorization.
13. `GamePaused` clears authorization.
14. `Shutdown` clears authorization.
15. Novablast continuous semantics remain unchanged.
16. Existing discrete family mappings remain unchanged.

### 12.2 HapticsManager tests

Add tests proving:

1. `WeaponFired/weaponFireStart` immediately reevaluates the saved R2 and submits `CutterBeam` without waiting for another observer sample.
2. R2 release submits `None` and retires authorization.
3. Weapon swap submits `None` while R2 is still held.
4. Game pause submits `None` while R2 is still held.
5. Shutdown submits `None` and clears saved R2.
6. Backend exceptions/failures remain contained.

### 12.3 Mixer tests

Add tests proving:

1. Cutter low-level state drives actuator channels 3/4 and leaves channels 1/2 exact zero.
2. High-level Cutter RMS is greater than low-level Cutter RMS.
3. High-level Cutter has greater oscillation frequency/zero-crossing density than low-level Cutter.
4. Cutter attack reaches full envelope after approximately 6 ms.
5. Updating Cutter level across blocks does not restart the attack or phase.
6. `None` produces exact continuous silence on the next block when no finite voice is active.
7. Finite voice + Cutter overlap stays bounded to `[-1, 1]` with reserved channels zero.
8. Novablast mixer regression behavior remains unchanged.

### 12.4 Controller observer tests

Add a focused regression for the newly required release-threshold notification:

- establish an observed R2 value inside bucket 0 but above release, e.g. 15;
- move to 12 without changing bucket;
- verify the observer receives the release-threshold update.

Also preserve existing tests for:

- first sample;
- bucket changes;
- exact 24 threshold crossing;
- disconnect/shutdown zero clear;
- throwing observer containment;
- no adaptive-trigger output changes caused by the observer.

### 12.5 Frozen regression gate

Before packaging, run the complete existing portable regression set plus focused v0.2.47 tests. Frozen production files for h4, fire-marker authority, and other explicitly locked subsystems must remain unchanged unless this spec names the file as part of the required Cutter implementation.

## 13. Expected implementation surface

Expected production files to change are narrowly limited to the haptics continuous-state path and the read-only observer threshold notification:

- `include/StarfieldDualSense/HapticTypes.h`

- `src/core/HapticsEngine.cpp`

- version/changelog/readme metadata for v0.2.47

`FireMarkerBridge.h`, `EffectsEngine.cpp`, HID arbitration, weapon trigger profiles, and the Windows audio transport should not require behavioral modification for this milestone.

## 14. Hardware acceptance criteria

v0.2.47 passes hardware acceptance when all of the following are true on a wired DualSense:

1. Holding/pulling R2 with the Cutter without an actual beam start produces no controller-body Cutter haptics.
2. Once the real Cutter beam starts, a sustained mining-tool texture is clearly felt in the controller body.
3. Pulling R2 farther makes the body texture noticeably stronger and somewhat faster/more aggressive.
4. The body texture complements, rather than masks or replaces, the already-approved Cutter adaptive-trigger texture.
5. Releasing R2 stops the body texture immediately with no perceptible tail.
6. Re-pressing R2 after a stopped pull does not create body haptics until Starfield produces a new real beam-start marker.
7. Weapon swap and pause cannot leave a stale Cutter buzz.
8. All previously locked controller behavior still works.

Hardware testing demonstrated this exact stale-beam condition when Cutter energy depleted while R2 remained held. The v0.2.47 follow-up therefore implements the previously deferred 300 ms real-`WeaponFire` heartbeat watchdog; the rest of the acceptance criteria and authority rules remain unchanged.
