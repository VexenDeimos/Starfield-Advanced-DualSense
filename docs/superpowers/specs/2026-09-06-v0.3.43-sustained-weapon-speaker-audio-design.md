# v0.3.43 Sustained Weapon Speaker Audio Design

**Date:** 2026-09-06  
**Baseline:** StarfieldDualSense v0.3.42  
**Version target:** 0.3.43.0  
**Runtime marker:** `0.3.43-sustained-weapon-speaker-audio`

## Goal

Add proper controller-speaker audio for **Arc Welder** and **Cutter** without turning their sustained beam sounds into repeated one-shot clips.

The controller speaker must begin the weapon-local loop only after Starfield posts the exact player Wwise loop-start event, keep that loop audible continuously for the full firing hold, and stop it immediately when the matching Wwise loop-stop event or any safety stop occurs.

The existing v0.3.42 one-shot speaker path for all 44 currently promoted logical profiles remains behaviorally frozen.

## Runtime Evidence

The Batch 3 discovery run established a real player-object lifecycle for both sustained weapons:

| Weapon | Loop start | Loop stop | Player object |
| --- | --- | --- | --- |
| Arc Welder | `0xBB87C268` — `WPN_Arc_Welder_Fire_Player_Loop_Play` | `0x46C5B7DA` — `WPN_Arc_Welder_Fire_Player_Loop_Stop` | `0x2` |
| Cutter | `0x8EDCB1C7` — `WPN_Cutter_Fire_Player_Loop_Play` | `0x40FF9B15` — `WPN_Cutter_Fire_Player_Loop_Stop` | `0x2` |

Each start event contains weapon-local trigger-press media plus actual `*_LP_01` loop bodies. Each stop event contains weapon-local trigger-release media. The same windows also contain shared cutter cross-layer material and separate reverb events; those are not required for the controller-speaker implementation.

The discovery run also established exact player-object finite cues for Arc Welder draw/holster/reload and Cutter draw/holster. Those can continue through the existing finite prepared-PCM path.

## Decisions Locked With Aubrey

1. **The sustained sound persists for the entire trigger hold.** A short start sound followed by silence is not acceptable.
2. **Wwise start is the authority.** Raw R2 movement can never fabricate a beam sound.
3. **Wwise stop is the primary normal stop.** Trigger release is also a safety stop so the controller never keeps sounding after the player lets go.
4. **No timer-based beam cutoff.** A legitimate long hold may continue indefinitely until a real stop condition occurs.
5. **One persistent weapon-speaker voice maximum.** Starting a new sustained weapon voice replaces any stale prior sustained weapon voice.
6. **Persistent weapon audio is isolated from finite speaker voices.** Existing gunshots, reloads, draw/holster sounds, UI audio, and controller voice playback retain their existing finite behavior.
7. **No synchronous Wwise/BA2/WEM work on gameplay callbacks.** All sustained PCM is prepared by the existing background weapon-audio pipeline before publication.
8. **Fail safe on missing readiness.** If the sustained family is not prepared, firing remains normal in Starfield but controller-speaker beam audio stays silent.
9. **Normal Starfield audio remains untouched.** The mod mirrors selected prepared media to the controller speaker and never suppresses/reposts the game event.

## Recommended Architecture

### 1. Add sustained metadata without repurposing normal one-shot cues

Keep `WeaponSpeakerCue` and the existing one-shot trigger behavior unchanged for the current catalog.

Add an optional sustained section to a weapon speaker profile/family. Conceptually:

```cpp
struct WeaponSpeakerSustainedCue
{
    std::string_view action;
    std::uint32_t startWwiseEventId;
    std::uint32_t stopWwiseEventId;
    std::uint64_t requiredGameObjectId;
    bool requireZeroExternalSources;
    float loopGain;
    std::vector<WeaponSpeakerVariant> loopVariants;
    std::vector<WeaponSpeakerVariant> startTransientVariants;
    std::vector<WeaponSpeakerVariant> stopTransientVariants;
};
```

Arc Welder and Cutter are the only v0.3.43 profiles that populate this metadata.

This keeps sustained lifecycle rules out of every existing one-shot cue and avoids changing what `ConfirmedWeaponFire` or ordinary `WwisePost` means for the 44 already-working profiles.

### 2. Prepare the sustained family in the existing background pipeline

Extend the immutable prepared family snapshot with an optional prepared sustained section:

```text
prepared start transient variants
prepared persistent loop variants
prepared stop transient variants
start/stop Wwise event ids + object gate
```

All WEM resolution, archive selection, decode, resample, loop shaping, and PCM preparation happen on `WeaponAudioPipeline`'s existing background worker.

Publication remains family-atomic. Arc Welder or Cutter becomes ready only when every required finite cue and every required sustained component for that family is prepared. An incomplete Arc Welder/Cutter family is not published; all other families remain live.

### 3. Use immutable shared PCM for the persistent voice

A sustained start callback must not copy a large loop buffer on Starfield's Wwise callback thread.

The prepared cache already publishes each family through `shared_ptr<const PreparedWeaponSpeakerFamily>`. Use an **aliasing shared pointer** (or equivalent immutable owner/reference pair) to hand the selected loop PCM to the speaker backend while keeping the family snapshot alive.

The Wwise callback therefore performs only:

```text
exact profile/event/object gate
-> immutable cache lookup
-> choose next prepared loop variant
-> enqueue small persistent-voice command/reference
-> return
```

No filesystem I/O, decode, resampling, or large PCM vector copy occurs in the callback.

Finite start/release/draw/reload/holster sounds continue through the already-proven finite prepared path.

### 4. Add one dedicated persistent prepared voice to `SpeakerMixer`

`SpeakerMixer` currently owns only finite voices whose cursors are erased when they reach the end. Add one separate optional `PersistentPreparedVoice` containing:

```text
immutable prepared PCM reference
cursor
gain
owner/generation token
loop resume frame
```

Render behavior:

- finite voices render exactly as today;
- the persistent voice renders in the same stereo speaker block and is included in the existing final clamp;
- when the persistent cursor reaches the loop end, it wraps to its prepared loop resume frame instead of being erased;
- the persistent slot does **not** consume one of `kMaxSpeakerVoices` finite slots;
- replacing the persistent voice is atomic from the render thread's point of view: one old voice is discarded and one new prepared reference becomes active.

There is never more than one persistent weapon-speaker loop.

### 5. Shape loop boundaries once during preparation

The selected `*_LP_01` media are authored as loop bodies, but the current PCM decoder does not depend on or expose Wwise loop-point metadata.

To avoid a click if the full decoded file boundary is not perfectly phase-aligned, sustained loop preparation adds a short deterministic boundary crossfade. The first pass begins at frame zero. The tail blends into the loop head, and subsequent wraps resume immediately after the head region consumed by that crossfade.

Target crossfade: **5 ms / 240 frames at 48 kHz**, shortened only when the source is too small.

This shaping is performed once on the background worker. The render thread performs no DSP allocation and no loop-boundary analysis.

### 6. Extend the speaker backend with explicit persistent controls

Add persistent operations through the existing speaker stack:

```text
IControllerSpeakerBackend
DualSenseAudioSpeakerClient
ControllerSpeakerManager
DualSenseAudioTransport
SpeakerMixer
```

Required semantics are equivalent to:

```cpp
setPersistentPreparedPcm(owner, sharedPreparedLoop)
clearPersistentPreparedPcm(ownerOrForce)
```

The transport queues only a small state/reference update for the audio thread. The render thread applies the latest persistent state before rendering the next block.

`replacePreparedPcm()` retains its current meaning for finite prepared audio and must **not** implicitly destroy the weapon persistent slot. This prevents existing controller voice replacement behavior from accidentally terminating a live beam.

### 7. Sustained lifecycle state belongs in `WeaponSpeakerPlayback`

`WeaponSpeakerPlayback` owns the logical authorization because it already knows the exact equipped speaker profile and receives Wwise observations.

For Arc Welder/Cutter:

**On exact Wwise Loop_Play**

- active profile must be the matching exact logical profile;
- event ID must equal that profile's sustained start event;
- game object must be `0x2`;
- external-source gate must pass;
- prepared sustained family must be ready;
- select the next loop variant deterministically;
- optionally submit the curated trigger-press transient;
- set/replace the persistent voice using a fresh owner/generation token;
- mark sustained authorization active.

**On exact Wwise Loop_Stop**

- if it belongs to the currently active sustained profile, immediately clear its persistent voice;
- revoke sustained authorization;
- submit one curated trigger-release transient;
- do not permit any held-R2 state to restart it.

Repeated start events while the same generation is already active must not stack another persistent voice. A new legitimate start after a stop creates a fresh generation and may select the next loop variant.

### 8. R2 is stop-only for speaker lifecycle

Feed the existing right-trigger observer into `WeaponSpeakerPlayback` as a lightweight safety input.

Rules:

- R2 can never authorize or start the persistent speaker voice;
- once a Wwise start has authorized a sustained voice, **R2 <= 12** immediately clears the persistent voice and revokes that authorization;
- later R2 movement while authorization is revoked cannot restart anything;
- a fresh Wwise Loop_Play event is required to start again.

This mirrors the safe authorization direction already established for continuous haptics while preventing raw input from creating audio during reloads or unrelated states.

### 9. Hard-stop conditions

Persistent speaker audio is immediately cleared and authorization revoked on:

- matching Wwise Loop_Stop;
- R2 release threshold (`<= 12`);
- any `WeaponEquipped` event before arming the new profile;
- `GamePaused`;
- opening `DataMenu`, `PauseMenu`, or `LoadingMenu`;
- `Shutdown`;
- speaker backend stop;
- audio endpoint invalidation/disconnect/reconnect boundary.

Closing a blocking menu or reconnecting the controller does not resume the old loop. Resume always requires a fresh exact Wwise Loop_Play.

The endpoint/transport layer must clear the persistent slot whenever the active audio endpoint is torn down so stale state cannot reappear after reconnect.

### 10. No fixed watchdog

Do not add a fixed-duration watchdog for Arc Welder or Cutter speaker audio.

A watchdog would violate the requirement that the sound persist for the full trigger hold. Cutter energy depletion or other in-game termination is expected to produce the real Wwise Loop_Stop; that event is the normal authority for ending a held beam even if the physical trigger remains depressed.

If hardware testing proves a real Starfield path can lose Loop_Stop while R2 remains held, gather that evidence first and design a state-specific fallback rather than adding an arbitrary timeout.

## Threading and Data Flow

### Background preparation

```text
WeaponAudioPipeline worker
  -> resolve Arc Welder/Cutter finite + sustained catalog media
  -> decode/resample PCM
  -> apply normal finite shaping
  -> apply 5 ms sustained loop boundary shaping
  -> validate complete family
  -> atomically publish immutable family snapshot
```

### Start path

```text
Starfield PostEvent callback
  -> WeaponSpeakerPlayback::observeWwise
  -> exact Arc Welder/Cutter + event + object gate
  -> immutable prepared family lookup
  -> choose loop variant / start transient
  -> enqueue small persistent reference state + finite transient
  -> return
```

### Render path

```text
DualSenseAudioTransport audio thread
  -> apply pending persistent-state update
  -> add finite prepared submissions as today
  -> SpeakerMixer renders finite voices
  -> SpeakerMixer renders persistent loop and wraps cursor
  -> clamp
  -> compose speaker channels with haptic channels
  -> WASAPI DualSense endpoint
```

### Stop path

```text
Wwise Loop_Stop OR R2 release OR safety event
  -> WeaponSpeakerPlayback revokes sustained authorization
  -> enqueue persistent clear
  -> optional release transient for Wwise normal stop
  -> next audio block contains no sustained voice
```

Safety stops such as pause, weapon swap, disconnect, or shutdown do not fabricate a release transient; they simply clear the persistent voice.

## Failure Isolation

- A sustained family preparation failure leaves only that family controller-speaker silent.
- A rejected persistent start does not affect haptics, triggers, controller input, lightbar, voice audio, finite speaker playback, or normal Starfield audio.
- A persistent command queue/update failure fails silent and is counted/logged; it never blocks a Wwise callback waiting on the audio thread.
- Endpoint invalidation clears persistent state before reconnect.
- The persistent voice cannot survive destruction of its prepared family because its immutable owner reference keeps the snapshot alive until the audio thread releases it.

## Testing Strategy

TDD is mandatory.

### Catalog and preparation tests

- v0.3.42 baseline first fails the new expectation that Arc Welder and Cutter have speaker profiles.
- profile totals become 46 and family totals become 43.
- physical prepared variant total becomes 444.
- Arc Welder and Cutter sustained start/stop IDs and required object `0x2` are exact.
- only curated weapon-local loop/press/release media are accepted.
- reverb, shared cross layers, NPC, environment, and unrelated media remain excluded.
- duplicate Cutter logical media prefer patch without double-counting.
- incomplete sustained data prevents only that family from publishing.

### Speaker mixer tests

- a persistent prepared voice renders nonzero audio beyond its source-frame length;
- cursor wraps without the voice being erased;
- prepared boundary crossfade avoids a large one-sample discontinuity at wrap;
- one persistent voice plus finite one-shots mixes and remains clamped;
- persistent voice does not consume finite `kMaxSpeakerVoices` capacity;
- replacing persistent voice leaves exactly one active persistent owner;
- owner-aware clear cannot accidentally clear a newer generation;
- force clear is exact silence for the persistent slot on the next block;
- `clearPrepared()` for finite replacement does not implicitly clear persistent weapon audio;
- full mixer clear/backend stop clears both finite and persistent audio.

### Transport/backend tests

- persistent start transfers a shared immutable prepared reference without copying the PCM frame vector on the producer path;
- latest persistent state replaces prior state instead of queueing an unbounded backlog;
- stop/clear wins over an older pending start;
- speaker client stop clears persistent state;
- endpoint invalidation/reconnect clears persistent state and does not resume without a new start;
- disabled speaker/category rejects persistent start safely.

### Playback lifecycle tests

For each of Arc Welder and Cutter:

- equip alone produces no persistent sound;
- raw R2 alone produces no persistent sound;
- wrong start event produces no persistent sound;
- right event on wrong game object produces no persistent sound;
- external-source start is rejected;
- exact player Loop_Play starts one persistent voice;
- repeated same-generation start cannot stack voices;
- the persistent voice remains authorized through an arbitrarily long simulated hold;
- R2 release threshold stops and revokes authorization;
- held R2 after stop cannot restart;
- exact Wwise Loop_Stop stops while R2 may remain physically held;
- a new exact Loop_Play after stop creates a fresh generation;
- weapon swap, pause, each blocking menu, and shutdown clear immediately;
- closing a menu does not resume a stale loop;
- normal Wwise stop may submit one release transient, but safety stops do not.

### Regression tests

- all v0.3.42 one-shot profile/playback tests remain unchanged and pass;
- all previous shared-family counts are updated only for the two newly promoted unique families;
- Quickstrike remains exact logical profile + Solstice audio family;
- Longfang remains exact logical profile + Orion audio family;
- Auto-Rivet gameplay gating remains frozen;
- existing Cutter/Arc Welder **haptics** tests remain unchanged and pass;
- weapon-audio background pipeline isolation remains intact;
- discovery remains inactive with zero targets;
- full haptics suite remains green.

## Hardware Acceptance Test

### Arc Welder

1. Equip and confirm draw speaker audio.
2. Hold R2 for approximately 2 seconds: press transient occurs once and the arc body remains continuously audible until release.
3. Hold R2 for approximately 8-10 seconds: no gap, finite cutoff, accumulating overlap, or repeated attack sound.
4. Release: loop ends immediately and release transient occurs once.
5. Reload: four finite mechanical cues play normally; no beam audio can begin from R2 during reload without a Wwise Loop_Play.
6. Start firing, then pause: beam stops and does not resume merely by unpausing while R2 remains held.

### Cutter

1. Equip and confirm draw speaker audio.
2. Hold R2 for approximately 2 seconds and then 8-10 seconds: laser body remains continuous for the full hold.
3. Release: loop stops immediately with one release transient.
4. Hold until an in-game energy-depletion stop if practical: Wwise Loop_Stop must terminate controller audio even if R2 is still held.
5. Start firing and swap weapons: persistent loop stops immediately and cannot leak into the new weapon.

After both tests, quit Starfield normally and verify the shutdown log contains no persistent speaker state surviving teardown.
