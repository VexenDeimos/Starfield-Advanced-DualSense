# v0.3.80 Land Vehicle State Recon Design

**Status:** Approved for implementation on 2026-09-10.

**Goal:** Establish a trustworthy, passive, diagnostic-only runtime model for player-controlled Starfield land vehicles (starting with the vanilla REV-8) so later haptic/adaptive-trigger work can be driven by actual vehicle state rather than controller-input guesses.

## Context

v0.3.79 is the accepted ship launch/landing baseline. The ship implementation proved a useful architectural rule: controller input may describe player intent, but game state must authorize controller effects. v0.3.80 applies that rule to land vehicles.

Land vehicles are a new ownership domain. They must not inherit on-foot or ship authority accidentally, and the recon milestone must not produce any new haptic, adaptive-trigger, speaker, or lightbar output.

## Scope

v0.3.80 will discover and log enough evidence to answer these questions on real hardware/runtime:

1. Is the player currently driving a land vehicle?
2. What exact runtime object/form represents the driven vehicle?
3. What reliable state changes mark vehicle enter, active driving, loading interruption, resume, and exit?
4. Which native values track forward/reverse drive demand, braking demand, speed/velocity, acceleration, boost state, and vertical/airborne behavior?
5. Are trustworthy wheel/contact/suspension or collision-impulse signals directly available?
6. Which Wwise events correlate with boost, suspension impacts, landing impacts, skids, and collisions, and can any of them serve only as corroboration where physics authority is weak?
7. Which raw controller inputs are useful as diagnostic annotations without becoming state authority?

The vanilla REV-8 is the first hardware target. The architecture must avoid hard-coding the REV-8 FormID as the definition of a vehicle so later Bethesda or modded land vehicles can use the same state model if their runtime shape is compatible.

## Non-goals

v0.3.80 will not:

- add land-vehicle haptics;
- add land-vehicle adaptive-trigger effects;
- add land-vehicle controller-speaker cues;
- change lightbar behavior;
- change native vehicle controls, steering, handling, physics, boost, camera, or game audio;
- guess vehicle context from R2/L2/stick input alone;
- promote unverified memory offsets into production behavior;
- change accepted v0.3.79 ship/on-foot/weapon behavior.

## Architecture

### 1. Dedicated land-vehicle recon domain

Add a small diagnostic-only land-vehicle subsystem rather than extending `ShipPilotContext` or `ShipPropulsionProbe` with land-vehicle conditionals. The ship and land-vehicle models have different authority sources and physics, and keeping them separate prevents cross-domain state leakage.

The portable core should use value objects that contain observations only. Runtime-specific pointer discovery and guarded memory reads remain in the Starfield adapter layer.

Proposed logical components:

- `LandVehicleReconState`: normalized snapshot of candidate vehicle context and readable telemetry.
- `LandVehicleReconProbe`: portable state machine that compares snapshots, derives diagnostic transitions, computes finite-difference acceleration where appropriate, and formats/returns bounded evidence.
- `GameStateAdapter::pollLandVehicleReconState()`: runtime adapter that resolves the player's current land-vehicle candidate and performs guarded passive reads.
- `Plugin.cpp`: owns activation/lifecycle integration, Wwise correlation windows, periodic logging, and version marker.

Names may be adjusted during implementation to fit existing project conventions, but responsibilities must remain separated.

### 2. Authority hierarchy

Evidence is ranked rather than treated equally.

**Tier A — authoritative context/state**

Preferred evidence directly ties the player to the active vehicle runtime object and exposes vehicle-owned state. Tier A evidence is required before later production vehicle haptics can be authorized.

**Tier B — authoritative/near-authoritative physics telemetry**

Vehicle velocity, drive/brake demand, boost resource/state, rigid-body motion, contact state, suspension/wheel state, or collision impulse observed from the active vehicle object. These values may drive later effects after hardware validation.

**Tier C — corroborating Wwise/event evidence**

Vehicle-specific boost, tire, skid, impact, suspension, or collision audio events may identify useful semantic boundaries. They are diagnostic corroboration unless later evidence proves a specific event is sufficiently exact to authorize a discrete effect.

**Tier D — player input annotation**

R2, L2, sticks, buttons, and boost-button state are recorded only to explain player intent and timing. They cannot establish vehicle ownership, acceleration, braking, wheel slip, collision, or airborne state by themselves.

v0.3.80 logs the tier/source for every promoted candidate so later work can distinguish fact from correlation.

### 3. Vehicle-context discovery

Implementation starts with public/CommonLib-exposed relationships and known engine abstractions before any offset probing. Candidate APIs/fields are inspected from the exact CommonLibSF revision used by the project on Windows.

A context candidate is accepted for logging only when the runtime can associate the player with the same vehicle object consistently across repeated polls. The probe records at minimum:

- player pointer/form identity;
- vehicle pointer/form identity;
- vehicle base/form type where exposed;
- whether the player-to-vehicle relationship is readable;
- whether the relationship remains stable across consecutive samples;
- menu/loading state at the observation time.

If no direct API exists, the runtime may add narrowly scoped guarded observation hooks to identify the vehicle object flowing through native vehicle code. Such hooks remain passive: observe arguments/return values only, call the original function unchanged, and fail closed when runtime identity or memory validity does not match expectations.

A menu name alone is not vehicle authority. Menu open/close data may corroborate entry/exit timing, but the player/vehicle relationship must be the primary proof.

### 4. Telemetry discovery

Once vehicle identity is established, v0.3.80 searches for telemetry in this order:

1. exposed CommonLib/RE fields or methods on the active vehicle/reference/physics object;
2. actor values, form configuration, or named runtime properties reachable from the active vehicle;
3. existing native functions/hooks whose arguments carry the desired state;
4. narrowly scoped memory lanes proven by repeatable correlation on the exact supported runtime.

For every numeric candidate, diagnostics include readability, finite/range checks, value, source identity, and correlation context. Invalid or non-finite reads are marked unavailable rather than coerced into meaningful state.

Target candidate groups:

- longitudinal speed / world velocity vector;
- drive demand / throttle intent native to vehicle simulation;
- reverse drive demand;
- brake demand;
- boost active/resource/recharge state;
- vertical velocity;
- vehicle orientation and angular velocity if cheaply available;
- grounded/contact count or wheel-contact evidence;
- per-wheel suspension compression/travel if exposed;
- collision/impulse magnitude and direction if exposed;
- skid/slip or tire-friction state if exposed.

The milestone succeeds even if some advanced groups (for example, individual suspension compression or slip ratio) remain unavailable, provided the log clearly proves which data are trustworthy and which require a later focused recon milestone.

### 5. Derived diagnostic values

Derived values are allowed only when based on trustworthy timestamped native observations.

The portable probe may compute:

- scalar speed delta and acceleration estimate from consecutive velocity samples;
- vertical acceleration estimate;
- enter/exit transition from repeated authoritative context snapshots;
- airborne candidate from authoritative contact evidence plus vertical motion;
- impact candidate from native collision evidence or a sufficiently abrupt velocity change, clearly labeled as derived rather than authoritative.

Derived estimates must include sample interval and source validity. No derived result is allowed to produce controller output in v0.3.80.

### 6. Wwise correlation

Reuse the existing zero-external Wwise capture path rather than creating a second audio hook. While authoritative vehicle context is active, record bounded vehicle-session Wwise observations with exact event ID, gameObject, callsite, returned playing ID, sequence, and timestamp.

The diagnostic report should make it easy to correlate manually performed actions:

- idle;
- gentle acceleration;
- full acceleration;
- braking;
- reverse;
- horizontal boost;
- vertical boost/jump;
- airborne coast;
- landing;
- small bump;
- hard terrain impact;
- deliberate collision;
- skid/turn if reproducible.

Wwise capture remains observational and normal game audio remains untouched.

### 7. Lifecycle and ownership isolation

Land-vehicle recon state must have explicit lifecycle handling independent of ship ownership.

Required behavior:

- on authoritative vehicle entry: begin a fresh vehicle session; do not restore stale samples;
- while active: accept only observations tied to the current vehicle identity;
- on `LoadingMenu` open: invalidate current live telemetry and prevent stale data from carrying through loading;
- after loading: reacquire vehicle authority only from fresh player/vehicle evidence;
- on authoritative vehicle exit: close the session and clear all current telemetry/correlation state;
- on ship pilot entry: land-vehicle authority must be absent/cleared;
- on shutdown: hard-clear the recon state and stop any vehicle-specific diagnostic capture.

v0.3.80 does not alter controller ownership when vehicle context is discovered; it only logs the context. Production ownership switching is deferred to the first haptic implementation milestone after recon is accepted.

## Logging and boundedness

Diagnostics use a dedicated `Land vehicle recon:` prefix and must remain usable in a real test log.

Avoid logging every frame. Use a bounded cadence plus transition/change logging:

- context transitions log immediately;
- core telemetry snapshots log at a modest fixed cadence while driving;
- material changes such as boost/contact/collision candidates log immediately;
- repeated identical uninteresting values are rate-limited;
- Wwise evidence uses bounded buffers and summary reports rather than unbounded accumulation.

Every diagnostic that references a raw lane/hook records enough identity to reproduce the finding on the supported runtime.

## Safety and compatibility

All runtime reads are passive/read-only and guarded. Observation hooks preserve original arguments/return behavior and never block or rewrite native vehicle code.

If a candidate pointer, relocation, vtable, runtime identity, or memory lane cannot be proven safe, that candidate is disabled and logged as unavailable. v0.3.80 must prefer missing telemetry over speculative telemetry.

The accepted v0.3.79 ship baselines are frozen. At minimum, regression/frozen-file checks protect ship pilot context, propulsion, ballistic, laser, particle, missile, EM, launch/landing, touchdown, controller-speaker routing, HID arbitration, and existing on-foot haptics.

## Versioning

- Project/DLL version: `0.3.80` / `0.3.80.0`.
- Runtime marker: `0.3.80-land-vehicle-state-recon`.
- Activation log explicitly declares `diagnostic-only`, `controllerOutput=none`, and the evidence sources that were successfully armed.

## Test strategy

### Portable tests

Test the recon state machine without Starfield runtime dependencies:

- first authoritative context sample anchors without fabricating an enter/exit sequence;
- repeated same-vehicle samples stay in one session;
- vehicle identity change ends the old session before accepting the new one;
- invalidation prevents stale telemetry from surviving;
- fresh post-load evidence can reacquire the same vehicle as a new live authority epoch;
- derived acceleration uses timestamped valid samples only;
- invalid/non-finite samples do not produce derived state;
- bounded evidence buffers cannot grow without limit;
- shutdown returns the probe to exact neutral diagnostic state.

### Source/runtime regressions

Require:

- v0.3.80 version/marker;
- dedicated land-vehicle recon component rather than ship-context reuse;
- passive/read-only discovery;
- no new controller output semantics;
- no native vehicle writes;
- input treated as annotation only;
- loading/exit/shutdown clear paths;
- existing Wwise capture reused rather than replaced;
- frozen v0.3.79 ship/controller paths retained.

### Windows gate

The gate must run the new focused recon tests plus the affected retained v0.3.79 ship/controller suites, build/install `StarfieldDualSense.dll`, and verify ProductVersion/FileVersion `0.3.80.0` before hardware reconnaissance.

## Hardware reconnaissance sequence

After the Windows gate passes, use one clean REV-8 session and record the full log:

1. stand on foot near the REV-8 for several seconds;
2. enter the driver seat and remain idle;
3. drive gently forward, then full forward;
4. brake to a stop;
5. reverse;
6. perform horizontal boost;
7. perform vertical boost/jump and remain airborne briefly;
8. land normally;
9. drive over visibly rough terrain/small rocks;
10. make one controlled low-speed collision and one harder safe in-game collision;
11. perform a sharp turn/skid attempt;
12. stop, idle, exit the vehicle, remain on foot, then quit normally.

The user reports action timing/feel only where needed; v0.3.80 itself emits no new controller effect to judge.

## Acceptance criteria

v0.3.80 is accepted when the Windows gate passes and a hardware log demonstrates:

- reliable player-driven land-vehicle enter/active/exit identity with no ship false positives;
- at least one trustworthy speed/velocity source;
- at least one trustworthy drive-demand or acceleration-correlated source;
- a trustworthy boost-state signal or a clearly isolated boost event candidate;
- loading and exit cannot leave stale vehicle authority alive;
- enough evidence exists to choose the next production milestone without guessing.

Braking, wheel/suspension contact, collision impulse, terrain material, and slip are desirable recon targets but are not allowed to block v0.3.80 if the runtime does not expose them cleanly. Any unresolved group becomes its own focused recon milestone before its corresponding haptic effect is authored.

## Expected next milestone

After v0.3.80 evidence is reviewed, the next milestone should implement only the vehicle effects supported by proven signals. The likely first production slice is vehicle ownership + base motion/acceleration + throttle/brake/boost presentation. Suspension, terrain, airborne landing, collision directionality, and slip/drift effects are promoted only after their authority is independently proven.
