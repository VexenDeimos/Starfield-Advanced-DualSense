# v0.3.57 Initial UI + Scanner Controller Speaker — Design

Date: 2026-09-06
Status: Approved in chat
Target version: 0.3.57
Target runtime marker: `0.3.57-initial-ui-scanner-controller-speaker`

## 1. Purpose

v0.3.57 is the first production controller-speaker build for Starfield UI and scanner sounds. It promotes a deliberately small set of hardware-observed, metadata-resolved Starfield Wwise events into additive DualSense controller-speaker playback.

The design must preserve the project’s established first-party-style principles:

- reuse Starfield’s installed audio assets rather than ship copies;
- keep Starfield’s original Wwise playback untouched;
- perform archive resolution and WEM decode off the game/audio callback path;
- route prepared PCM through the existing controller-speaker stack;
- fail soft per cue;
- keep UI/scanner behavior independent from weapon, comms, ship, digipick, crafting, haptics, triggers, lightbar, and touchpad behavior;
- prefer exact runtime evidence over guessed or synthesized sounds.

This version is intentionally an untuned hardware baseline. It does not add controller-specific EQ, trimming, compression, custom fades, per-cue gain shaping, debounce, or cadence suppression.

## 2. Promoted event catalog

Exactly five Starfield Wwise events are promoted in v0.3.57:

| Event ID | Expected Wwise event name | Role |
| --- | --- | --- |
| `0x05234A32` | `UIMenuGeneralFocus` | General menu navigation/focus |
| `0x5C8034FC` | `UIMenuGeneralOK` | Confirm/accept |
| `0x7956E9B0` | `UIMenuGeneralCancel` | Back/cancel |
| `0x12D8B183` | `UIMenuMonocleOpen` | Scanner open |
| `0x1F770B61` | `UIMenuMonocleClose` | Scanner close |

All five require the hardware-validated UI game object `0x3` at runtime.

The following previously investigated events are explicitly not promoted in this version:

- `UIItemFocus` / `0x06D80D5E`;
- Star Map and Surface Map rollover events;
- `UIMenuSkillsSkillFocus`;
- mission-specific selection/toggle events;
- any other broad HUD/notification candidate.

`UIItemFocus` is excluded because it resolves to the same underlying media already observed behind map rollover behavior and is not needed for the first minimal playback set.

## 3. Architecture choice

### 3.1 Selected approach

Use the existing Wwise startup-resolution infrastructure once, but publish UI/scanner audio into a dedicated UI playback subsystem:

- `UiSpeakerPreparedCache` owns immutable prepared PCM for the five promoted cues.
- `UiSpeakerPlayback` owns runtime qualification and submission behavior for UI/scanner observations.
- `ControllerSpeakerManager` remains the centralized submission/category/output policy layer.
- `SpeakerCategory::ScannerUI` is the category for all five promoted cues.

The UI subsystem must not be folded into `WeaponSpeakerPlayback`. Weapon and UI speaker behavior share lower-level resolver/decode/output infrastructure, but retain separate logical ownership and tests.

### 3.2 Rejected alternatives

A second independent UI Wwise resolver worker is rejected because it would redundantly index/read the same Starfield archives.

Shipping extracted WEM files is rejected because the game already contains the assets. v0.3.57 must not require an ESP, ESM, BA2, BSA, or bundled Bethesda audio file.

## 4. Startup preparation flow

The existing background Wwise worker remains the only startup preparation worker for this area.

Preparation order is:

1. Prepare/index the shared Wwise metadata/archive resolver once.
2. If UI/scanner speaker playback is enabled, resolve and decode the five promoted UI/scanner events first.
3. Publish each successful UI cue independently into `UiSpeakerPreparedCache`.
4. If weapon speaker playback is enabled, continue into the existing weapon preparation flow unchanged.
5. If weapon speaker playback is disabled, skip the expensive weapon preparation stage entirely.

UI/scanner preparation must not depend on:

- `SpeakerWeapons=true`;
- `DebugLogging=true`.

Weapon preparation must not be required merely to make the five UI sounds ready.

### 4.1 Per-cue preparation requirements

A cue is publishable only when all of the following succeed:

1. the event ID is one of the exact five catalog entries;
2. Wwise metadata resolves the event;
3. the resolved Wwise event name exactly matches the expected catalog name;
4. exactly one playable media asset is selected for the promoted cue;
5. WEM bytes can be read from the installed Starfield archives;
6. decode succeeds;
7. prepared PCM is structurally valid for the existing speaker path.

A failure in one cue must not prevent the other four from becoming ready.

### 4.2 Audio shaping policy

v0.3.57 preserves native decoded amplitude and full decoded duration.

Do not add:

- EQ;
- controller-specific filtering;
- trimming;
- fade-in/fade-out shaping;
- compression;
- limiting beyond the existing mixer/output safety behavior;
- per-cue loudness normalization;
- per-cue gain tuning.

The existing global `SpeakerVolume` remains authoritative.

## 5. Runtime capture and qualification

### 5.1 Existing PostEvent hook only

The current `AkSoundEngine::PostEvent` interception remains the only Wwise hook.

For every intercepted call:

1. the original Starfield `PostEvent` must execute exactly once;
2. its arguments and returned playing ID must remain authoritative and unchanged;
3. UI/scanner mirroring is purely additive;
4. the mod must never stop, replace, repost, suppress, or reroute the original Starfield UI sound.

### 5.2 Production UI observation filtering

The v0.3.54-v0.3.56 broad discovery behavior is not a production runtime requirement.

When broad discovery is inactive, the thunk should enqueue a UI observation only when all of these are true:

- production UI/scanner playback is armed;
- the event has zero external sources;
- the event ID is one of the exact five promoted IDs.

This avoids filling the bounded UI queue with unrelated world/HUD Wwise traffic that would later be discarded.

The existing bounded deferred-queue principle remains: if the controller-copy queue is full, drop the controller-copy observation rather than block Starfield’s Wwise thread.

### 5.3 Runtime playback qualification

`UiSpeakerPlayback` accepts an observation only when:

- the event ID is one of the five promoted IDs;
- `gameObjectId == 0x3`;
- no external source is present;
- the matching prepared cue is ready;
- the effective UI/scanner speaker configuration is enabled;
- shutdown has not begun.

Any failure produces no controller-speaker submission and does not affect original game audio.

## 6. Playback semantics

All accepted cues submit through the existing prepared-PCM path:

`UiSpeakerPlayback` -> `ControllerSpeakerManager::submitCaptured(...)` -> `SpeakerCategory::ScannerUI` -> existing backend/mixer -> proven DualSense speaker route.

Each cue uses a deterministic `CapturedSoundIdentity` derived from its Wwise event ID and resolved media ID, consistent with the project’s captured-audio identity approach.

### 6.1 GeneralFocus policy: native-exact cadence

The user explicitly selected native-exact behavior for `UIMenuGeneralFocus`.

Therefore v0.3.57 must not implement:

- debounce;
- same-event deduplication;
- a 30 ms anti-spam window;
- “latest wins” replacement;
- cadence throttling;
- held-stick special handling.

Every qualifying `UIMenuGeneralFocus` observation is independently submitted with finite-voice behavior and `replaceExisting=false`.

If fast navigation produces overlapping focus sounds, the existing speaker mixer handles them naturally. The mixer’s fixed voice capacity remains an emergency safety bound, not a tuning policy.

### 6.2 Confirm/cancel semantics

Every qualifying `UIMenuGeneralOK` and `UIMenuGeneralCancel` event is independently submitted as a finite prepared voice with no replacement policy.

### 6.3 Scanner open/close semantics

Every qualifying `UIMenuMonocleOpen` and `UIMenuMonocleClose` event is independently submitted as a finite prepared voice.

Opening and immediately closing the scanner may allow the tail of the open sound to overlap the close sound. v0.3.57 must not forcibly cut off one to play the other.

## 7. Configuration behavior

No new TOML setting is added.

The effective production gate for all five cues is:

```text
ControllerSpeaker = true
AND
SpeakerScannerUI = true
```

Required behavior:

- `ControllerSpeaker=false` disables the controller-speaker subsystem globally, including these five cues.
- `SpeakerScannerUI=false` disables UI/scanner preparation, production UI capture arming, and UI/scanner submissions.
- `SpeakerWeapons=false` does not disable UI/scanner preparation or playback.
- `DebugLogging=false` does not disable UI/scanner preparation or playback.
- `SpeakerComms`, `SpeakerDigipick`, `SpeakerCrafting`, and `SpeakerShipSystems` remain independent.

`SpeakerOutputMode=ControllerOnly` retains its existing remote/radio-voice-specific original-output policy. v0.3.57 must not reinterpret that setting as permission to suppress Starfield’s native UI/scanner or weapon audio.

## 8. Diagnostic cleanup

The automatic v0.3.55/v0.3.56 UI WEM extraction behavior is diagnostic evidence and must not remain active in normal v0.3.57 production runtime.

v0.3.57 should resolve and decode installed game assets directly in memory. It must not automatically write UI WEM files into `StarfieldDualSenseDiagnostics` each time Starfield starts.

Debug logging may report bounded readiness and runtime counters, including:

- per-cue ready/unavailable state;
- submitted UI/scanner cue count;
- rejected observation count by broad reason;
- dropped deferred UI observation count.

Logging must not be required for behavior to function.

## 9. Failure behavior

The feature is fail-soft and fail-open with respect to Starfield audio.

Examples:

- If `UIMenuGeneralCancel` no longer resolves after a game update, Cancel controller playback is unavailable but the other four cues remain usable.
- If an expected event name changes for a known ID, that cue is rejected during preparation rather than blindly playing an unexpected asset.
- If decode fails, no fallback tone is synthesized.
- If the UI observation queue is full, the controller copy may be dropped; Starfield’s original Wwise call still proceeds normally.
- If the controller speaker backend is unavailable, original game audio continues normally.

There is no fallback beep, substitute media, or asset guessing in v0.3.57.

## 10. Shutdown and lifecycle

Shutdown must preserve the project’s quit-safe ordering.

Required UI/scanner shutdown sequence:

1. disarm production UI/scanner capture;
2. stop accepting new UI/scanner observations;
3. drain or retire already-deferred UI observations without submitting after speaker shutdown begins;
4. stop/join the shared startup worker if still active;
5. stop the controller-speaker backend through the existing runtime shutdown path.

No prepared UI PCM may be submitted after `ControllerSpeakerManager` begins shutdown.

The UI subsystem must not change TESHit registration/unregistration, haptics shutdown, USB reset behavior, trigger/lightbar teardown, or weapon persistent-voice teardown.

## 11. Implementation boundaries

Expected new logical units:

- `include/StarfieldDualSense/UiSpeakerPreparedCache.h`
- `src/core/UiSpeakerPreparedCache.cpp`
- `include/StarfieldDualSense/UiSpeakerPlayback.h`
- `src/core/UiSpeakerPlayback.cpp`

Expected integration edits are limited to the files needed to:

- expose the five-cue catalog and preparation path;
- prepare UI cues in the existing background Wwise worker before weapon preparation;
- add exact-ID production filtering to the existing UI observation path;
- integrate `UiSpeakerPlayback` with `Plugin.cpp` lifecycle/configuration;
- version, document, and test v0.3.57.

Do not modify the proven USB speaker channel mapping or unrelated haptics/trigger/lightbar/touchpad behavior.

If implementation reveals that the existing worker API cannot support UI-first publication without materially restructuring weapon-pipeline interfaces, stop and upgrade/review the design rather than silently broadening scope.

## 12. TDD requirements

Production behavior must be introduced under red-green-refactor.

Tests must prove at least the following:

1. The production UI catalog contains exactly the five approved event IDs and exact expected Wwise names.
2. `UIItemFocus`, map rollover, Skills focus, and mission-specific IDs are not in the production catalog.
3. All five runtime events require game object `0x3`.
4. Zero-external is required; external-source observations are rejected.
5. Every qualifying `UIMenuGeneralFocus` observation is accepted; there is no debounce/cadence limiter.
6. Repeated focus observations produce separate finite submissions with `replaceExisting=false`.
7. OK, Cancel, MonocleOpen, and MonocleClose route independently.
8. Wrong event ID, wrong game object, external source, missing preparation, or shutdown state produces no submission.
9. `SpeakerScannerUI=false` disables UI preparation/capture/playback.
10. `ControllerSpeaker=false` disables it globally.
11. `SpeakerWeapons=false` does not disable UI preparation/playback.
12. `DebugLogging=false` does not disable UI preparation/playback.
13. One failed cue does not poison successfully prepared siblings.
14. The original Wwise `PostEvent` is called exactly once and returned playing ID is unchanged.
15. v0.3.57 production runtime performs no automatic UI WEM extraction.
16. Existing weapon, VO, speaker, haptics, trigger, lightbar, touchpad, TESHit, and cumulative v0.3.48-v0.3.56 regressions remain green.
17. The proven logical-mono-to-physical-Channel-2 USB speaker mapping remains unchanged.

## 13. Hardware acceptance

After the Windows/MSVC build gate passes and the installed DLL reports `0.3.57.0`, validate on a wired DualSense:

1. Normal menu navigation produces the native `GeneralFocus` sound from the controller.
2. Hold the stick/D-pad for rapid navigation and judge native-exact repeated focus cadence without hidden throttling.
3. Confirm/accept produces the expected `GeneralOK` controller sound.
4. Back/cancel produces the expected `GeneralCancel` controller sound.
5. Scanner open produces `UIMenuMonocleOpen` from the controller.
6. Scanner close produces `UIMenuMonocleClose` from the controller.
7. Starfield’s normal UI/scanner audio remains audible and unchanged in the game mix.
8. `SpeakerScannerUI=false` disables all five controller copies while leaving other speaker categories alone.
9. `ControllerSpeaker=false` disables all controller-speaker output through the existing master policy.
10. Weapon speaker, remote VO, haptics, adaptive triggers, lightbar, touch shortcuts, and shutdown behavior remain unchanged.

Any complaint about focus chatter, cue loudness, cue duration, scanner overlap, or tonal balance is recorded as hardware tuning evidence for a later version. v0.3.57 itself does not pre-tune those characteristics.

## 14. Non-goals

v0.3.57 does not:

- add generic HUD notifications;
- add map-specific rollover playback;
- add Skills-specific playback;
- add mission-specific playback;
- promote `UIItemFocus`;
- add scanner haptics;
- change ship behavior;
- change weapon speaker behavior;
- add new controller-speaker config keys;
- ship custom or extracted Starfield audio assets;
- create an ESP/ESM/BA2/BSA;
- suppress original Starfield UI/scanner audio;
- tune individual UI cue gain/EQ/duration;
- debounce or throttle GeneralFocus.

## 15. Release/package expectations

The user-facing package remains an SFSE-plugin-style package. No game plugin/archive is added solely for these sounds.

As with the existing workflow, implementation handoff must provide only changed/new files relative to the accepted v0.3.56 source baseline, plus a manifest, SHA-256, and testing procedure. The full source tree must not be repackaged.

The Windows handoff must include the established DLL install command followed immediately by ProductVersion/FileVersion verification with expected version `0.3.57.0`.
